# Fork changes and validation

This fork is based on [Project Maya](https://github.com/mw00/project-maya),
upstream commit `26aacb6` (v1.1.49). The local changes below were validated on
2026-11-02. Upstream authorship, model licenses, and the normal setup process are
preserved. These changes are not an upstream release or a general speed claim.

## Windows copied-expert registration

With copied RAM experts and a helper GPU, registering the whole RAM arena could
leave the Windows NVIDIA driver unable to provide the prompt path's CUDA0 memory.
The observed failure was `the prompt path's room could not be handed back`,
followed by unknown expert tables and a required engine restart.

RAM allocation and CUDA host registration now have separate budgets:

- Query the visible WDDM adapters' DXGI non-local budgets. Portable registrations
  use the smallest allowance, retaining 5% or at least 1 GiB of headroom.
- Register whole existing layer/NUMA arenas within that allowance, preserving
  successful registrations. The RAM data remains allocated even when unregistered.
- Allow direct prompt DMA only for layers whose NUMA parts are all registered;
  use the existing pinned staging path for other layers.
- Preserve the existing later-buffer probe and release only this attempt's pins
  when that probe needs room. An unavailable WDDM budget uses staging.
- Keep the existing Linux, HIP, and NVIDIA TCC registration path.

The budget policy was adapted from [Basalt](https://github.com/jesdga95/basalt)
and is credited in `LICENSE`. See `include/strata/platform/host_pin.hpp`,
`src/ds4/ds4_model.cu`, and the copied-expert section of [SETTINGS.md](SETTINGS.md).
The host-only budget/range test is registered with CMake and included in CI.

On the tested 128 GiB PC, an 80 GB RAM arena registered about 46 GB rather than
all 80 GB. The allowance depends on the driver, adapter budgets, and concurrent
applications; this is not a fixed 46 GB limit. The remaining RAM copies use staging.

## Codex Responses compatibility

The Responses adapter supports the client shapes used by Codex without changing
the model's underlying tool syntax:

- Namespace-qualified function tools and custom/freeform tools, including Code
  Mode and `apply_patch`. A custom tool's raw input travels internally as a JSON
  string argument and returns publicly as `custom_tool_call` with its call ID.
- Custom-input SSE events, public stored-response shapes, and tool-result replay
  so the conversation can continue after a call.
- Client-executed `tool_search`, discovered tools, and Responses Lite
  `additional_tools` declarations.
- Reasoning replay through a `maya.r1:` token requested with
  `include: ["reasoning.encrypted_content"]`. This token is base64 JSON,
  **not encrypted**, and must be handled as plaintext.
- The `reasoning.context` and `text.verbosity` client hints, and the `auto`, `low`,
  `high`, and `original` image-detail hints. The configured template and image
  encoder remain authoritative.
- `reasoning.summary` values `auto`, `concise`, `detailed`, and `null`. The previous
  rejection prevented Codex requests from running. These are accepted as display
  hints; the server still returns `reasoning_text`, an empty summary array, and
  the same reasoning replay. No separate summarization inference is introduced.
- JSON Schema output alongside custom tools, retaining the existing validation.

Grammar declarations describe the tool input to the model; they are not enforced
by constrained decoding. OpenAI-hosted web search and other hosted tools are not
executed by Maya. Foreign encrypted reasoning tokens are not decoded. See
[RESPONSES.md](RESPONSES.md) for API behavior and limitations.

Codex App provider routing and selector installation are maintained separately in
[custom-model-provider-in-codex-app](https://github.com/LesterLyu/custom-model-provider-in-codex-app).
This Maya fork does not install Codex account settings, credentials, catalogs,
or New API channels.

## Helper GPU monitoring

The hardware monitor now samples a configured DeepSeek helper even when it is
outside `cfg.gpu`, the target model's layer-device list. Numeric
`CUDA_VISIBLE_DEVICES` / `HIP_VISIBLE_DEVICES` mappings are resolved to physical
indices. This changes telemetry discovery, not layer placement. Unresolvable UUID
mappings fall back to the existing list rather than guessing a physical index.

## Reproducible local settings

The following are **deployment choices**, not new defaults or new model features
in this fork. Apply them to a config generated by Maya, keeping its own model,
tokenizer, executable, and library paths:

| Setting | Tested value |
| --- | --- |
| Model | DeepSeek-V4.1-Flash-1017, Maya-XS v2 |
| Target device / tensor parallel | `--gpus 0`, `--tp 1` |
| Context | `--max-context 524288` |
| Prompt chunk | 32768, the existing default |
| RAM experts | `--mmap-experts off`, `DS4_WARM_CAP_GB=80` |
| Host registration | `DS4_COPY_PIN=1` |
| Visible devices | `CUDA_VISIBLE_DEVICES=0,1` |
| Helper | `DS4_HELPER=1`, `DS4_HELPER_GB=12` |
| Helper recent slots | `DS4_HELPER_RECENT=4` |
| Speculation | `--dspark on`, drafter on the target GPU |

The hardware used was a Ryzen 9 9950X, RTX 5090, RTX 5060 Ti, and 128 GiB RAM.
The helper's room must also accommodate desktop applications. These RAM/VRAM
budgets are specific to this setup, not recommendations for smaller machines.
No additional low-memory process-killing monitor was installed. The launchers,
machine paths, model files, logs, backups, API credentials, and private routing
configuration are not part of this repository.

For the local Codex model entry, context/max-context were set to 524288 and the
auto-compaction threshold to 440000 on Windows and WSL, while keeping the other
models' settings. Those private catalogs are not committed. The server and the
client's context limits must agree.

## Validation and limits

| Check | Result and scope |
| --- | --- |
| Native Windows build | Release, CUDA 13.3, SM 120, build parallelism 10; succeeded |
| Host pin policy | Host-only allowance arithmetic and registered-range boundary checks passed on Windows and with the Linux CI compiler flags |
| Dashboard regression | 49 tests passed, including helper discovery and visibility mapping |
| HIP mapping check | No unmapped CUDA names in code compiled by the HIP backend |
| Long prompt / memory restoration | Fresh 42,009- and 129,009-token prompts and follow-up requests passed with the 80 GB RAM budget and partial registration, at the earlier 256K context setting |
| 512K context | Engine loaded, health endpoint reported 524288, config persisted; short API/Codex requests passed. A full 512K input has not been tested |
| KV allocation | About 233 MiB at 256K and 463 MiB at 512K on this build; these are pure KV allocations, not total engine VRAM |
| Responses regression | 90 tests, 4 skipped, remaining tests passed; includes summary hints, custom-tool SSE, tool continuation, schemas, storage, and jobs |
| Real Codex clients | Windows and WSL Code Mode and freeform `apply_patch` calls completed and continued through the existing API gateway |
| Summary compatibility | An explicit `summary=auto` API request and a Codex turn configured with `model_reasoning_summary=auto` completed through the gateway |

No controlled old/new model speed comparison is claimed. The old main weight
shards were removed during the requested XS v2 migration; the unchanged Engram
tables were retained and reused. That migration used the existing upstream
installer/packer rather than a new weight format in this fork.

Compaction can still require a fresh prefill when its rendered prefix changes.
One observed large compaction did so; isolated current-CLI requests preserved the
ordinary prompt prefix. This fork does not claim to resolve every compact/cache
case, and accepting `reasoning.summary` is a separate protocol fix.
